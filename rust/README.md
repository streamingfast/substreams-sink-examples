# Substreams Sink Rust

This repository show cases a functional base Rust project that consumes a Substreams `.spkg` (local or remote file).

To run:

```bash
SUBSTREAMS_API_KEY="<StreamingFast API Key>" cargo run -- https://mainnet.eth.streamingfast.io:443 https://github.com/streamingfast/substreams-eth-block-meta/releases/download/v0.5.1/substreams-eth-block-meta-v0.5.1.spkg db_out
```

## Details

The presented Rust project contains a `SubstreamsStream` wrapper that handles automatic reconnection in case of error. It is implemented as a Rust `TryStream` which enable consuming the retryable stream easily using standard Rust syntax:

```rust
let stream = SubstreamsStream::new(...);

loop {
   match stream.next().await {
      None => { /* Stream completed, reached end block */ },
      Some(Ok(BlockResponse::New(data))) => { /* Got a BlockScopedData message */ },
      Some(Err(err)) => { /* Fatal error or retry limit reached */ },
   }
}
```

The `main.rs` file accepts three arguments: the substreams endpoint (in the form `http(s)?://<url>:<port>`), the location of the `.spkg` file to use for the request, and the output module's name to stream from.

### Incomplete Implementation

#### Cursor Persistence

For now `cursor` handling is not properly loaded/saved to database, something that would be required on a production system to ensure the stream is resumed at the right location and that a block is never miss.

Should be implemented in [main.rs](./src/main.rs) in `persist_cursor` function and in `load_persisted_cursor`.

> **Warning** If you don't implement cursor persistence, if your process restart, it will start back from specified `start_block` (currently hard-coded to `0`).

#### Logging

We use `println` statements within [main.rs](./src/main.rs) and [substreams_stream.rs](./src/substreams_stream.rs) to demo what is happening within the codebase. Those, specially in [substreams_stream.rs](./src/substreams_stream.rs), should be replaced to be logged to a logging system.

Also, more places could be instrumented to log extra details.

#### Block Undo Signal

`BlockUndoSignal` must be treated as "delete every data that has been recorded after block height specified by block in BlockUndoSignal". In the example above, this means you must delete changes done by `Block #7b` and `Block #6b`. The exact details depends on your own logic. If for example all your added record contain a block number, a simple way is to do `delete all records where block_num > 5` which is the block num received in the `BlockUndoSignal` (this is true for append only records, so when only `INSERT` are allowed).

This is left to be implemented by you how to deal with that.

> **Warning** It's done using `unimplemented!` macro which will panic if an undo signal is received, so be warned for a production system. Undo signals on Ethereum Mainnet happen around 5-10 times a day, even less so you might miss the fact that they exist when testing.

### Protobuf and gRPC Stack

The example uses [buffa](https://github.com/anthropics/buffa), the protobuf implementation `substreams` 0.8+ moved to, instead of `prost`. Message types are generated by buffa and the gRPC client is [connectrpc](https://github.com/connectrpc/connect-rust) (`connectrpc` crate), which is built on buffa and speaks the gRPC protocol over HTTP/2 (`Protocol::Grpc`) — Substreams endpoints serve gRPC, so no server-side change is needed.

`tonic` cannot be used here: its generated clients are bound to `prost` messages, so mixing it with buffa types does not work. Moving off `prost` for a native sink therefore means moving off `tonic` too.

Things worth knowing when reading the code:

- Generated messages are checked in under `src/pb` (buffa) and `src/pb_connect` (service stubs). `src/pb/mod.rs` and `src/pb_connect/mod.rs` are written by hand: remote `buf` plugins cannot run buffa's packaging step, so they stitch together the per-package files.
- Singular message fields are `MessageField<T>` which deref to a default instance when unset (`data.clock.timestamp.seconds`, no `unwrap()`). Use `.as_option_mut()` / `.into()` to mutate or build them.
- Decoding is `Package::decode_from_slice(&bytes)` (`use buffa::Message`).
- The `Blocks` RPC returns zero-copy views, `SubstreamsStream` converts each message to an owned `Response` with `to_owned_message()`. Auth is sent as the `x-api-key` header.
- JSON support and unknown fields are disabled in codegen (`json=false`, `unknown_fields=false`, `no_json`) to keep the dependency tree and generated code small.
- `connectrpc` requires Rust 1.88+, see [rust-toolchain.toml](./rust-toolchain.toml).

### Protobuf Generation

Protobuf generation is done using [buf](https://buf.build/) with remote plugins, in two steps:

- [buf.gen.yaml](./buf.gen.yaml): message types with `buf.build/anthropics/buffa` into `src/pb`.
- [buf.gen.connect.yaml](./buf.gen.connect.yaml): gRPC client stubs with `buf.build/connectrpc/rust` into `src/pb_connect` (only the `Stream` service of `sf.substreams.rpc.v4`).

Both pull the published [Substreams Buf Module](https://buf.build/streamingfast/substreams) pinned to a version and generate only what the sink needs (the `rpc` v2/v3/v4 and `v1` packages that `Package`, `Request` and `Response` reference). `buf` can be installed with:

```bash
brew install bufbuild/buf/buf
```

> **Note** See [other installation methods](https://buf.build/docs/installation/) if not on Mac/Linux (`brew` can be installed on Linux).

Then regenerate with:

```bash
buf generate
buf generate --template buf.gen.connect.yaml
```

Files are overwritten in place. `src/pb/mod.rs` and `src/pb_connect/mod.rs` are hand-written and never touched by `buf`; delete stale generated files by hand if a package is dropped.

> **Note** To bump the Substreams protos, change the pinned version in both `buf.gen*.yaml` files. If new packages are needed, add them to the `paths` list and to the `mod.rs` files.
